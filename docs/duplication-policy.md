# Політика дублювання та синхронізації даних (Data Duplication & Consistency Policy)

## 1. Обґрунтування необхідності дублювання даних

У сучасних розподілених системах та архітектурі мікросервісів (Bounded Contexts за DDD) суворе дотримання третьої нормальної форми (3NF) на рівні всього підприємства є антипатерном. Використання спільних таблиць або прямих розподілених запитів (cross-database joins) між різними бізнес-контекстами призводить до:
* **Жорсткої зв'язаності (Tight Coupling):** Зміна схеми одного контексту ламає функціонал іншого.
* **Каскадних відмов (Cascading Failures):** Падіння сервісу каталогу унеможливлює роботу кошика та оформлення замовлень.
* **Втрати історичної достовірності (Historical Inconsistency):** Якщо ціна або назва товару в каталозі зміниться, сума у вже оплачених замовленнях минулих періодів не повинна спотворюватися.

Для вирішення цих проблем застосовується контрольована денормалізація та **політика дублювання даних (Data Duplication Policy)**.

## 3. Детальний аналіз ключових сценаріїв

### 3.1. Патерн "Історичний знімок ціни" (Price Snapshotting Pattern)
* **Проблема:** Якщо в таблиці `OrderItems` зберігати лише `ProductId` і при формуванні звіту чи накладної підтягувати `Price` з таблиці `Products` через JOIN:
  1. Будь-яка зміна ціни товару (інфляція, акція) заднім числом змінить загальну суму старих замовлень та бухгалтерію.
  2. Перейменування товару виробником спотворить опис товару у фіскальному чеку.
* **Рішення:** У контексті `Orders & Fulfillment` (Проєкт №1) таблиця `OrderItems` містить поля:
  ```sql
  [ExternalProductId] INT NOT NULL,
  [ProductSKU]        NVARCHAR(50) NOT NULL,
  [ProductName]       NVARCHAR(200) NOT NULL,
  [UnitPrice]         DECIMAL(18,2) NOT NULL
  ```
  Ці поля заповнюються **один раз** у момент оформлення замовлення. Вони ніколи не оновлюються з каталогу автоматично після того, як замовлення перейшло у статус `Pending` чи `Paid`.

### 3.2. Патерн "Логістичний знімок одержувача" (Shipping Snapshot)
* Клієнт може мати профіль із дефолтною адресою, але для конкретного замовлення інструментів або мастила вказує доставку на СТО чи поштомат біля гаража.
* Таблиця `OrderDeliveries` фіксує точні контактні дані отримувача та адресу відправки в окремому записі, ізольованому від будь-яких подальших змін у профілі покупця.

### 3.3. Реплікація метаданих у MongoDB (Specs & Compatibility Context)
* Каталог товарів у Проєкті №2 веде суворий реляційний облік цін, брендів та залишків на складах.
* Проєкт №3 у MongoDB зберігає поліморфні технічні специфікації (в'язкість мастила, допуски, крутний момент) та дані сумісності авто.
* При створенні нового товару в Проєкті №2 генерується подія `ProductCreated`, яка передає базові реквізити (`Id`, `SKU`, `Name`, `BrandCode`). MongoDB підсистема створює шаблон документа специфікацій у колекції `product_specifications`.

## 4. Стратегії збереження узгодженості та вирішення колізій

### 4.1. Transactional Outbox Pattern
Для гарантії того, що зміна стану в базі даних SQL Server не відбудеться без відправки повідомлення в чергу (і навпаки), використовується патерн **Transactional Outbox**:
1. Бізнес-операція (наприклад, зміна статусу замовлення через `usp_ChangeOrderStatus`) оновлює таблицю `Orders` та записує повідомлення в службову таблицю `OutboxMessages` в межах **однієї ACID-транзакції**.
2. Фоновий воркер (Background Worker / Outbox Publisher) читає невідправлені події з `OutboxMessages` та публікує їх у брокер повідомлень.
3. Після підтвердження публікації запис позначається як відправлений (`ProcessedAt = SYSUTCDATETIME()`).

### 4.2. Ідемпотентність обробників (Idempotent Consumers)
Оскільки брокери повідомлень гарантують доставку "щонайменше один раз" (At-Least-Once Delivery), споживачі подій у MongoDB та SQL Server використовують унікальні ключі дедуплікації (`MessageId` або `OrderId + Timestamp`), запобігаючи повторній обробці однакових подій.

### 4.3. Вирішення колізій паралельної зміни цін
* Якщо клієнт поклав товар у кошик за ціною 1500 грн, а під час фінального натискання "Оплатити" ціна в каталозі змінилася на 1600 грн:
  * Сервіс замовлень перед викликом транзакції порівнює хеш ціни або версію прайсу.
  * Якщо зафіксовано різницю, клієнту повертається помилка з пропозицією підтвердити оновлену вартість кошика перед списанням коштів.
